- SPAWN-START-SIGNAL-TIMEOUT01 (`contract_version` stays 15; no tool input schema, no migration, no new error code): a new session that never reports its `SessionStart` within the start delay (`startSignalTimeoutMs` of its harness, else 60 s) gets `readiness: failed` (`no_start_signal`), even when a PTY byte had made it `ready`, and is closed with `resume_timeout`. The new output (`readinessDetail`, the `no_start_signal` value, the `session.failed` event) is recorded in the section "15". The explicit delay of the daemon (`firstStartTimeoutMs`) wins over the one of the harness; a closed session stops counting against `children_cap` once its process is gone (up to 5 s after the failure, then the manager's next `create_session` passes); a process that survives the force kill for 10 s (`forceKillGraceMs`) no longer holds the slot for ever: its session is closed without its exit and the daemon logs a `kill_failed` warning (the grace applies to every `close()` and to the relaunch after a model change, not only to this timeout: after the SIGKILL and the grace the session is closed even if the process still runs, a relaunch then closes it with `launch_failed` instead of starting a second process, and the `kill_failed` warning carries the session id but no pid; the output of a replaced or closed process is dropped); the close reason of a close requested during the escalation replaces `resume_timeout` unless the daemon stops in the meantime; a late `SessionStart` or PTY byte does not bring the session back; a failed readiness is cleared when the session is resumed at boot or reopened. See `docs/launch-health.md`.
- WORKTREE-SETUP-HOOK01 (no tool schema, REST view or `contract_version` change): the project post-create script must now be owned by the daemon's user, besides being an executable file writable by its owner only; otherwise it is refused with `unsafe_permissions` (`PATCH /api/projects/:id` and at each run). Hardening: a project hook already configured whose script is not owned by the daemon's uid now gets `unsafe_permissions` at every worktree creation (the creation does not fail) and is refused on save by `PATCH`. `scripts/worktree-setup.sh` (install + husky) is a script a human sets as the post-create hook of the OpenFleet project; nothing found in a repository is run on worktree creation. See `docs/worktrees.md`.
- ESCALATION-REOPEN-F8A01, one reopen of an arbiter decision (decision F8A of the escalation design; `contract_version` stays 15, which is unreleased): each question of `submit_plan_questions` takes the optional `reopens: <question id>`, the id of a question the arbiter decided on the same ticket, with new executed evidence in `resolution`. The tool's input schema is unchanged (`questions` is an array of objects the daemon parses), so the contract pin does not move; only the description of the tool changed. The first reopen goes to a new arbiter run (counted in `maxArbiterRunsPerTicket`) that sees its earlier decision and the evidence. A second contest, a reopen of the question that holds the answer to the first reopen, never reaches an arbiter: the question joins the single open escalation of the ticket with the reason `arbiter_dispute`. There is no third round. A reopen of a question that is not `decided`, of an unknown id, of another ticket or manager, of a decision already reopened, or without executed evidence is refused `invalid_body` and stores nothing. No new error code. Migration `060_plan_question_reopens.sql` (additive, down file `060_plan_question_reopens.down.sql`) adds the nullable `plan_questions.reopens_batch_id` and `reopens_question_id`. When several decided questions of the ticket share an id, `reopens` targets the most recent one.

- ESCALATION-ATTENDED-REST400-01 (REST, no tool schema or `contract_version` change): a request to `/api/sessions/:id…` or `/api/managers/:id…` whose body carries `attended` (true or false, alone or next to `name`, `mission`, …) is refused with 400 `invalid_body` and the reason "attended is immutable after creation", so a combined body such as `{ name, attended: false }` never succeeds with the flag ignored. ## 15 — 2026-10-30

ESCALATION-LADDER01, the escalation ladder: a manager sends its questions to the daemon, which answers the ones it can, asks an arbiter for the ones that need a second opinion and puts only the ones that need a human on the human list.

- `submit_plan_questions` (manager): sends the questions of a plan note, each with a class; the daemon routes every question to the manager itself, to the arbiter or to the human. Answers the batch id and the route of each question.
- `report_arbiter_opinion` (arbiter only): reports a decision per question of the batch and an opinion on the criteria (`favourable`, `unfavourable`, `not_asked`). The daemon writes the decisions, the plan note sections and the journal and tells the manager.
- `approve_plan_criteria` (manager): asks the daemon to approve the criteria of a ticket; the daemon writes the `criteria_status` column itself.
- Behaviour change, a call that succeeded before now fails: the harness tool `AskUserQuestion` is refused to a manager session, attended or not (command policy rule `manager-ask-user-via-ladder`, profile `manager`); the refusal points to `submit_plan_questions`.
- Escalation setting: a project can set its escalation policy (`escalation`, `PATCH /api/projects/:id`, admin token; `null` clears it). `contract` and `security` always stay on the human list.
- `get_argus_status`: `manager` gains one field, `escalationPolicy`, the policy of the manager's project (the defaults when the project sets none). Read only.
- BREAKING vs 14 (STATUS-NO-MISSION-BODY01): `get_argus_status` no longer returns `manager.missionText` (up to 64 KiB on every call). `manager` carries `missionBytes` (size of the stored mission in UTF-8 bytes) and `missionSha256` (hex sha256 of the stored mission) in its place; a client that read `manager.missionText` from this tool now calls `get_manager_mission`. The REST `GET /api/managers/:id` view and the desktop are unchanged: they still carry `missionText`. What the change guarantees is that the mission adds only its digest (two small fields) to the answer: the whole answer stays under 2 KB for a manager with a 30 KB mission, no child and no scheduled event (the test's setup); children, `blockedTickets` and `scheduled_events` still add their own bytes. The description of `get_argus_status` now names `get_manager_mission`; a tool description is not in the contract pin, so the pin did not move for it.
- Contract 15 was unpublished when `get_manager_mission` and the output change were added to it (2026-10-30: `git tag --list` printed nothing, no release); this is why the version did not rise again (see `docs/mcp-contract.md`).
- `get_manager_mission` (manager, added): returns `missionText` (the stored mission followed by the blocks of the notes its `@note:` mentions point to, expanded as `get_note` does: depth 2, 64 KiB budget, notes of the caller's project or shared), `missionBytes` and `missionSha256` (of the stored mission alone, the same two values as `get_argus_status`). Without a project the mission comes back unexpanded; a mention of a note of another project that is not shared is listed "not resolved". Optional `manager_id`: only the caller's own id is accepted. A session that is not a manager is refused `not_a_manager`; another manager's id is refused `outside_lineage` (no widening: before, only the manager itself read its mission, through `get_argus_status`). No new error code.
- `get_manager_mission` paging (MISSION-READ-PAGING01, added to the unpublished 15, so `contract_version` stays 15): the tool takes the optional `offset` (bytes, integer from 0) and `max_bytes` (positive integer, can only lower the cap), the same names and bounds as `get_note`, and keeps the same cap of 24 KiB (`NOTE_READ_SAFE_BYTES`) per answer, through the same code (`boundedReadView`). The mission and its expanded mentions come back whole, without `complete`, when they fit. Otherwise the stored mission comes back whole with `mentionsIndex` (`[{id, type, bytes, readWith}]`, the mentions are not expanded) and `complete: false`, and the manager reads each mention with `get_note`. A stored mission that alone exceeds the cap is paged with `offset`: `missionText` holds the slice, with `offset`, `bytes`, `totalBytes`, `truncated`, `nextOffset`, `nextAction` (`get_manager_mission offset=<n>`) and `complete: false`, `mentionsIndex` on the first page only; the pages put end to end give the stored mission byte for byte. An `offset` past the end gives an empty last page, as in `get_note`. The input schema moved, so `contract.pinned.json` was refreshed. Before, an answer could reach about 64 KiB, which the agent harness spills to a file. Also: a mission whose `missionNoteId` is set no longer expands that note into itself when it mentions it: the mention reads `--- @note:<id>: not expanded (mission note: read it with get_note note=<id>) ---` (the mission text is not the note, so "already expanded" would be wrong here), and the `mentionsIndex` lists the same note with `readWith: get_note note=<id>`. `NoteService.expandText` takes an optional `rootNoteId` and `rootNoteSkipReason` (the expander's `rootNoteSkipReason` option, default "already expanded", so `get_note` is unchanged); `NoteService.getTextMentionIndex` indexes the mentions of a text that belongs to no note.
- Scape import (no tool schema change): a reference to `get_argus_status` (with or without the `mcp__scape__` prefix) is written `get_manager_mission` in three forms only: `manager.missionText` right before it (`manager.missionText of get_argus_status`), `manager.missionText` right after it (`get_argus_status: manager.missionText`, `get_argus_status → manager.missionText`, `get_argus_status().manager.missionText`; the field is dropped with it), and a sentence that has a reading verb (read, re-read, fetch, lis, relis, lire, relire, consulte, consulter), then "mission", then the tool. Every other `get_argus_status` reference keeps its name, such as "check the progress of the mission and your children with get_argus_status". The sentence form stops at `.`, `!`, `?`, `,`, `;` and a line break, and allows at most 300 characters in each of its two gaps (verb to "mission", "mission" to the tool), about 600 in all; `read-only` is not a reading verb. Verbs not covered: reads, reading, fetches, lit, consultez, open, ouvre and any other form than the ones listed. Known limits: a sentence cut over two lines is not followed; a comma or a semicolon between "mission" and the tool cuts the sentence, so "Read your mission at startup, using get_argus_status" and "Relis ta mission, via get_argus_status" keep `get_argus_status`; and the period of `manager.missionText` cuts the sentence in "Read the mission (manager.missionText) with get_argus_status", which keeps `get_argus_status` too. The law prose an earlier import wrote (`import scape clean-laws`) is rebuilt with the earlier rewrite, without this rule, so it still matches what is stored.
- Scape re-import of missions already imported: the planned record changes, so the next import reconciles each manager (`reconcileRecord`). A manager whose stored record equals what the last import wrote, and that has no local profile fields (`expertise`, `pulseActions`), is `updated`: `updateManager` rewrites its `mission_text`, `pulse_seconds`, `children_cap` and the model of its session, and `profile_rev` rises by one. - CHILD-SILENCE-WAKE01 (added to the unpublished 15, no tool schema change, so `contract_version` stays 15 and the pin does not move): when a manager messages one of its live children, the daemon arms a silence check for that child, 10 minutes by default. The single observation point is `SessionService.sendMessage` (`onAgentMessageSent`), so every tool that writes agent to agent is covered: `send_session_message`, `message_parent`, `message_argus`, and the no-go line of `report_ship_verdict`. A new message to the same child replaces the deadline (one per child); the idempotent replay of an already queued `message_id` does not. The check is cancelled when the child writes to its manager or when the child or the manager closes. At the deadline the manager receives one line that opens `[scheduled event "silence_check", due <local time>]` and names the child, its id, the minutes since the message and the age of its last state change; the line says that the reminder is not listed by `list_argus_events` and not cancelled by `cancel_argus_event`. Nothing is sent when the child is closed, when its state changed less than the delay ago, or when the manager is `disabled`. The check is not a scheduled event: it is not in `list_argus_events` or `get_argus_status.scheduled_events`, does not count in the 20 pending events of a manager, stays inside the manager's own lineage, and is kept in memory only (a daemon restart drops the pending checks; accepted). No migration, no new error code. OpenFleet has no `report_progress` tool; `message_parent` is the child's signal. Known limits: a reviewer's `go` verdict sends no message, so it does not cancel the check; several children silent at once wake the manager once each (no grouped line); a check that is skipped because the child changed state recently is not re-armed.

ALWAYS-REPRO01, every claim of a review report cites a reproduction or says it is not reproduced. A breaking change, on purpose.

## 12 — 2026-10-29

CI-WAIT-WAKE01, wake a manager when the CI of a pull request it watches finishes.

- `watch_pr` added: `{ repo, number }`, `repo` as `owner/name`. The daemon polls the checks of the pull request with the user's GitHub CLI (`gh pr view --json state,headRefOid,statusCheckRollup`, fixed argument list, no shell; the daemon reads no token) and tells the manager once per head sha through a scheduled event titled `ci.finished`, delivered late rather than lost.
