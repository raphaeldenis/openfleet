# Playbook runs

**In brief.** A playbook of script cells runs only after a human approved its digest. The runner starts each script itself, with no shell, journals every step before it starts, and masks the value of every secret before anything is stored or answered. A daemon killed in the middle of a step marks the run `needs_review` at the next boot and never starts the step again. This page describes the runner of script cells (PBK-P3a), `http` cells (PBK-P3b-http), `readFromStore` and `writeToStore` cells (PBK-P3B-STORE-TOOL), and `manual` and `waitFor` cells (PBK-P4a1); and the `retry` field, the `forEach` edge and the `subPlaybook` cell (PBK-P4A2); `tool` cells (PBK-P3B-TOOL) come later. A trigger starts a run with the RUN `run_playbook` (see `docs/triggers.md`).

## Who can do what

| Action | Human (admin REST) | Agent (MCP) |
|---|---|---|
| Read the approval digest | `GET /api/playbooks/:id/approval` | no tool |
| Approve | `POST /api/playbooks/:id/approve` `{ digest }` | no tool |
| Run | `POST /api/playbooks/:id/run` `{ inputs }` | `run_playbook` (approved playbook of the project of the session; see "The run tools") |
| Read a run | `GET /api/playbook-runs/:id`, `GET /api/playbook-runs?playbookId=` | `get_playbook_run`, `list_playbook_runs` (runs of the project of the session) |
| Answer a manual step | `POST /api/playbook-runs/:id/steps/:seq/resume` `{ decision }` with the header `x-human-proof` (single-use nonce of the desktop app) | never: no tool answers a manual step |

The admin token is not a proof of a human gesture, by design: whoever holds it, an agent that can read `admin.token` included, can read the digest, approve and run a playbook it wrote itself, and the daemon cannot tell it from a human (there is no desktop nonce on these routes). The approval separates the admin from the MCP token and nothing more: it stops an agent that has only its MCP token, as `agent_locked` does. Treat the admin token as the authority to run the scripts under the script roots; the desktop app is where a human is expected to read the digest before confirming it.

## The approval

The digest is the sha256 of the canonical JSON of the name, the inputs, the cells, the policy and the sha256 of every script file the cells name. `GET .../approval` answers the digest and the scripts it pins; `POST .../approve` takes that digest back and is refused with `approval_digest_mismatch` when the playbook is no longer the one that was read. Any edit of the playbook clears the approval, so an agent that edits an approved playbook leaves it inert until a human approves again.

A run checks the approval twice: at launch (the digest of the content as stored, the sha256 of each pinned file) and right before each step (the file that is about to start). A file that changed, is gone or is unsafe to start fails with `script_changed`; content that no longer matches the digest is `playbook_unapproved`.

## Scripts

A script cell names a `program`: a literal path, relative to a script root or absolute inside one. A token in it is refused: an approval cannot pin it. The real path, after symlinks, stays inside the root; the file belongs to the daemon's user, is not writable by group or others and is executable. The roots are `playbooks.scriptRoots` of `config.json` (absolute paths, at most 16); with none, no script runs.

The script starts with the basic environment of the daemon (`PATH`, `HOME`, `USER`, `LOGNAME`, `LANG`, `TMPDIR`, `SHELL`, `LC_*`) plus the `env` of the cell, in its own process group, in the folder of the file. The group is killed when the step ends, whatever the way it ends: after an exit (0 or not) every process the script left running dies with it, so a script cannot leave background work behind; at the timeout of the cell (`timeoutSeconds`, 10 minutes by default) and at the shutdown of the daemon the group gets SIGTERM, then SIGKILL after a grace period of 2 seconds. The run slot is released after that kill, and every timer of the step is cancelled when the step is answered: no signal reaches the group afterwards, so a process group id reused by another program is never signalled. A process that leaves the group on its own (`setsid`) is out of reach. A script whose `spawn` fails, for instance because a variable holds a NUL, fails the step with `script_spawn_failed`; the error of the system, which can carry the value of a variable, is neither logged nor stored.

Known limit: the hash is read, then the file is started; a file that changes in between is not seen. The owner and permission checks narrow that window to the user's own processes.

## The journal

A run is written `running` before its first step. A step is written `running` before its script starts, then `succeeded`, `failed` or `needs_review` with its masked output. A step that does not succeed ends the run `failed` with the code of the step (`script_failed`, `script_timeout`, `script_changed`, `untrusted_reference`, `unresolved_reference`, `step_limit_exceeded` ...).

At boot every run and step left `running` is marked `needs_review` with the code `interrupted`: a step that was running may have had its effect, so nothing starts it again. A script that outlives a daemon killed with `kill -9` is not stopped by the next boot; the step is only marked. A new run of the playbook is allowed.

## Masking

The values of the secrets the playbook references are resolved when the run starts (`secret_not_connected_on_this_device` refuses the run, and nothing is written, when this device holds none). The output of a step goes through the shape-based layer of `redact.ts`, then through the value-based masker: the plain, URL-encoded, base64 and JSON-escaped forms of each value become `[secret:NAME]`. The inputs of the run are masked the same way before they are stored. A script that hashes, splits or re-encodes the value defeats the masker; the approved script is the control. The cap of the output never cuts a secret: the step keeps the cap plus the length of the longest spelling of the secrets of the run, and the cut moves back before a secret that crosses it, on stdout and on stderr alike. An unexpected error of a step is masked with the values of the run before it is logged.

## http cells

An `http` cell calls a host the human approved: `allowedHosts` in the policy lists exact lowercase host names (IDN in punycode) or IPv4 literals, with no wildcard, port or userinfo. The list is empty by default, so no host is reachable, and it is part of the approval digest: changing it clears the approval.

The name is resolved once. A name that resolves to a loopback, private, link-local, shared or multicast address, or one of whose answers does, is refused with `http_address_blocked`; the connection then goes to the address that was checked, so a DNS answer that changes in between has no effect. A literal IP written in `allowedHosts` is the human's choice and is not range-checked. The scheme is `https`; `http` is accepted only for a loopback address. A redirect is never followed (`http_redirect_refused`). A response outside 2xx fails the step with `http_status_failed` and keeps its masked body. The step answers `status` and `output` (the body, capped like a script's output and treated the same way: shape-based layer, value masker, control characters). Response headers are not kept and no cookie is sent or stored.

A secret may stand in the headers and the authentication only; the url and the body refuse it. The output of an earlier step is refused in the authority of the url, the headers and the authentication, and accepted in the path, the query and the body, where it cannot steer the request elsewhere. Each token is checked in its place again at run time. Headers with a line break, headers the client sets itself (`Host`, `Content-Length`, `Transfer-Encoding`, `Connection`, ...) and resolved headers over 16 Ki characters fail the step before anything is sent.

A step found running at boot is `needs_review`, like any step: the request may have reached the server, so it is never sent again.

Known limits: a server that echoes a secret in a form the daemon cannot recognise (hashed, split, or combined with other text before base64) defeats the masker, as for scripts. A literal IP in `allowedHosts` can point at a private address on purpose.

## Store cells

A `readFromStore` or `writeToStore` cell works on a table of the project of the playbook, and on no other: the data store service checks the owner of the table on every call, with the project of the playbook, so a table of another project and a table that does not exist both fail the step with `store_not_in_project`, and the answer says nothing more. The table (`storeID`) and the columns (`columns`, `whereColumnID`, `sortColumnID`, `naturalKeyColumnID`, the keys of `rowMappings`) are ids. They may hold literals and `{{inputs.x}}` but never the output of a step: the save refuses it with `untrusted_reference`, and the runner checks again before it touches the table. A value (`whereValue`, the values of `rowMappings`) accepts any token except a secret.

A read filters on one column (`whereColumnID` and `whereValue` go together, else `store_filter_incomplete`; the comparison is an equality), sorts on one, and answers `rowCount` and `output`, the rows as JSON (`[{ id, data }]`, only the columns asked for). It answers 100 rows when the cell sets no `limit` and at most 1000 whatever the limit; an answer over 256 Kio of UTF-8 bytes (not characters: a text of multi-byte characters weighs its bytes) fails the step with `store_read_too_large` and keeps no row (it is never cut). The limit and the columns are applied by the read itself, not after it: the rows stream out of the database one at a time and only the cells asked for are built; without a sort the scan stops at the row that fills the `limit` (a read of `limit: 1, columns: []` on a table of 5000 rows reads one row), with a sort the matching rows are held to be sorted. In both cases the rows kept are counted in bytes as they arrive and the read stops, with `store_read_too_large`, at the row that crosses 256 Kio, so a table of large cells is never loaded whole. The rows go through the same treatment as a script's output: the shape-based layer, the value masker, the control characters.

A write inserts one row, or, when the cell names a `naturalKeyColumnID`, upserts on the natural key the table holds. That column must be exactly the natural key the table holds when the step runs: an id that is no column, a column of another table, a column that is not the key, the former key of a table that has changed it, and any column on a table that has no natural key all fail the step with `store_natural_key_mismatch` before anything is written (a table with no key takes inserts only, with no `naturalKeyColumnID`). It answers `outcome` (`inserted` or `updated`) and `rowId`, never the cells. Every value passes through the value masker before the write, so the value of a secret never reaches a table. The history of the table names the author `playbook run <run id>`, with the actor kind `trigger` (the automation kind the history accepts without a migration).

Values are written as text: a number, json or select column takes a string that is valid for it, and a text that is not fails the step with `store_value_rejected`. The failure of a store step is a code of the journal and nothing else: `store_column_unknown`, `store_natural_key_mismatch`, `store_value_rejected`, `store_row_cap_reached` (the table is at its 10,000 rows), `store_read_failed`, `store_write_failed`. No row, no value and no error text goes in the activity log, in the journal of the failure or in the logs (the log line names the type of the error only). The activity log keeps the ids of the run, as for any run.

A step found running at boot is `needs_review`, like any step. A write is never replayed: the row may be written. A read could be replayed without harm, but the journal says what ran, so it is marked and not started again either. A write that is committed when the daemon stops leaves its step `running`; at boot the step becomes `needs_review` and the write is not made again (the row is in the table once).

Known limits:
- The secret mask is per run. It knows the secrets the playbook of the run references, nothing else. A secret value that is already in clear in a table, and that the current run does not reference (the secret of another playbook or run, or an old value after a rotation), is not masked when a read returns it: it can reach the journal of the step and the REST view of the run. The sentence "the value of a secret never reaches a table" holds for the values the run knows, not for a table that someone else filled.
- The loop guard of the triggers (`tableSource`) sees only the writes of a session acting as an agent. The write of a run is seen by it only if the run was started by a trigger, through the active run of that trigger (PBK-TR6, PR #434); otherwise it carries no chain depth. This change must be merged after #434.
- With a sort, the matching rows are held in memory to be sorted, up to 256 Kio of cells; a larger set fails with `store_read_too_large` even if `limit` is small.
- Rows are read with the cells they hold, an empty cell is left out of the answer (an absent cell and a cell set to `null` read the same).

## Manual cells

A `manual` cell puts a question to a human and waits. The run and the step become `waiting_manual`; the question (`playbook_manual_requests`) holds the prompt with its tokens resolved and every secret value masked, and the instant its wait ends: `timeoutSeconds` of the cell after the question, at most 24 hours (the default). Nothing is started while a run waits, and the run holds no process and no timer.

- **The count.** A waiting run is not one of the 4 runs at once and does not count among the runs that await a review. It holds its playbook (one run per playbook). At most 50 runs per project may wait: a new run of a playbook that has a `manual` cell is refused with `playbook_waiting_backlog` at that count, and a run that reaches its `manual` cell at that count fails the step with the same code.
- **The answer.** `POST /api/playbook-runs/:id/steps/:seq/resume` with `{ "decision": "approve" | "reject" }`, under the admin token and with the header `x-human-proof`: the single-use operator nonce that the desktop app mints for the action `playbook.resume_manual` on exactly this step (scope kind `playbook_run`, the run id as scope id, the sequence number of the step as name). A request without the proof, with a nonce for another run, another step or another action, or with a spent nonce is refused with `human_proof_required`. The admin token alone is not a proof of a human gesture, and no MCP tool answers a manual step: an agent never resumes a run. The answer is recorded once (`manual_already_answered` for the second, even when two arrive together). An approval goes on with the cell after the manual cell, with `{{steps.<id>.decision}}` equal to `approved`; a rejection ends the run `failed` with the code `manual_rejected`.
- **The checks at the answer.** The order is: the proof is present; the wait is still open (`manual_wait_expired` ends the run `failed`); a place among the 4 runs at once is free (`playbook_run_busy`); the proof is good; the playbook is still the approved content the run started from (the digest of its name, inputs, cells, policy, which holds the allowed hosts, and the sha256 of its scripts, then its revision and flow). A playbook edited, unapproved or changed on a script while the run waited closes the question and ends the run `needs_review` with the code `playbook_changed_while_waiting`, and the answer is refused with the typed code (`playbook_unapproved`, `script_changed` or `playbook_conflict`): the run is never continued. Then the secrets are read again from the keychain of this device (`secret_not_connected_on_this_device` leaves the run waiting), and the masker of the run is built from them before the answer is recorded: a value that cannot be masked (a keychain changed outside the API, a value too short) refuses the answer and leaves the question pending and the run waiting, so no run is left `running` with nothing to execute.
- **What is not kept.** No secret value is stored while a run waits: the journal holds masked outputs, and they are read back as they are at the answer. The inputs of the run were stored masked, so an input whose value is a secret reads as `[secret:NAME]` after the answer.
- **The end of a wait.** The runner has no timer for it: a wait whose time is over is ended (the question `expired`, the step and the run `failed` with `manual_wait_expired`) when the daemon boots, when any run starts, when someone answers and when a playbook is deleted, on the injected clock. A deletion sweeps only the waits of the project of the playbook, and only after the writer, the lock against agents and the revision passed: a refused attempt to delete a playbook settles no wait, of its project or of another one (the other sweeps stay global).
- **The order of the refusals does not depend on the secrets.** The masker of the secrets read for an approval is built after every check of the answer (the end of the wait, the question still open, the place among the runs, the approved content, the tree budget), so a secret that turns out too short (`secret_too_short`) after a slow read never hides `manual_wait_expired`, `playbook_unapproved` or `manual_already_answered`; it refuses the answer only when nothing else does, and the question stays pending.
- **The tree budget read back.** Only an approval reads the journal of the parked step. The budget is absent only for a step with no output or an object without a `treeBudget` key (what the versions before the budget wrote); an output that cannot be decoded, an array, a text, a number, a boolean, or a budget with a missing or out-of-bounds count (both counts are required) is invalid: the approval closes the question, puts the run in review with the journal-only code `parked_tree_budget_invalid`, and answers `manual_already_answered` (409, terminal, no budget value shown; the question is closed, so the nonce is spent and a new human gesture has nothing to answer). The closing yields to the end of the wait: at or after `expiresAt` it answers `manual_wait_expired`. A rejection never reads the journal, so it ends the run `failed` whatever the journal holds.
- **The resume prepared before the answer.** An approval rebuilds, from the journal, the point the run resumes from (the outputs of the steps that succeeded and the cell after the manual one) BEFORE the answer is recorded and the run set running again. If that rebuild fails (an output of an earlier step that cannot be decoded, a parked step the journal no longer holds), the question is closed, the run and its step go to `needs_review` with the journal-only code `resume_preparation_failed` (no wire code), and the answer is `playbook_conflict` (409): no run is left running without a walk, holding a place among the runs at once, which no cancellation could reach. The closing yields to the end of the wait, as the closing of the other refusals does: at or after `expiresAt` it answers `manual_wait_expired`. The same holds when the wait ends while the approval of the playbook is verified: the answer is `manual_wait_expired` and the run ends `failed`, never a review the journal does not hold.
- **A boot.** A run found `waiting_manual` stays so and can still be answered; a step found `running` is `needs_review`, as before.

Known limits: the desktop app has no screen yet for the question (the run screen and the Inbox card are UI2); until then the answer goes through the REST route and the nonce command of the app. A wait that nobody ends with a boot, a start, an answer or a deletion stays `waiting_manual` after its time, and is counted against the cap of 50 until one of them happens.

## WaitFor cells

A `waitFor` cell holds the step until its `predicate` is true. The predicate is evaluated by the evaluator of conditions that the edges and the triggers use (no `eval`, no expression language), on this scope: `inputs`, `steps` (the outputs so far) and `wait.elapsedMs` / `wait.now` (the injected clock). No secret is in the scope. The step answers `elapsedMs` and `evaluations`.

It evaluates at once, then sleeps `pollMs` on an injected timer between evaluations: 5 seconds by default and never less than 1 second, whatever the cell asks (the schema accepts 100 ms; the runner raises it). The last sleep is the time left before the ceiling. The step fails with `wait_for_timeout` at the ceiling of the cell (`timeoutSeconds`, 600 by default, 86,400 at most) or after 1000 evaluations, whichever comes first. The stop of the daemon cancels the timer and ends the step `needs_review`; a step found running at boot is `needs_review` and is not evaluated again.

## Retry

A cell with `retry: { maxAttempts, until, backoffMs }` is executed again until it is done or the attempts are spent. An attempt is done when the cell succeeded and `until` holds; a cell with an empty `until` is done at its first success, so `retry` then only repeats a failed attempt. `until` is evaluated by the evaluator of conditions of the edges, on `inputs`, `steps` (the output of the attempt that just ended stands under the id of the cell) and `attempt.number`.

- **The journal.** Every attempt is a step of its own, written `running` before it starts and settled after it. Every attempt counts among the 1000 step executions of the tree of runs. At most 20 attempts and a backoff of one hour at most (the bounds of the schema), and each attempt has its own timeout: there is no deadline for all the attempts together.
- **The end.** A failed attempt that is not the last one is followed by the backoff, then the next attempt. The last attempt decides: it fails with its own code (`script_failed` ...), or, when it succeeded and `until` still does not hold, with `retry_exhausted`.
- **The backoff** sleeps on the injected timer (`backoffMs` 0 arms none), never on a wall-clock wait of the test. The stop of the daemon cancels it and ends the run `needs_review`.
- **No second effect.** A run is refused with `playbook_not_runnable`, before anything is written, when a cell that retries is a `writeToStore`, an `http` cell whose method is not GET or HEAD, a `manual` cell or a `subPlaybook` cell: a second attempt would repeat what the first one may have done. A script retries on the author's word: the approved script must be safe to run again. The same holds for GET and HEAD, which are only repeatable by convention: an approved endpoint can have side effects on a GET, and a timeout can come after the effect. The method gate stops the writes the runner knows about, not the effects of the endpoints a human approved.
- **Never after a crash.** A run found `running` at boot is `needs_review`, in the middle of a backoff as anywhere else: no attempt is started again, whatever number of attempts were left.

## forEach

An edge `next: [{ to, forEach }]` runs its target cell once per element of the list `forEach` names (`inputs.<path>` or `steps.<id>.<path>`), in order, with `{{item}}` (a text or number as it is, an object as canonical JSON) and `{{index}}` (from 0). Then the run goes on with the edges of the target.

- **The list.** A list, or the text of a step output that holds a JSON list. Anything else fails the run with `for_each_source_invalid`, before any element runs. An empty list runs nothing and goes on.
- **The caps.** 100 elements per edge and 1000 iterations per run: an edge over either fails the run with `for_each_limit_exceeded`, before any of its elements runs. Every iteration is a journaled step and counts among the 1000 step executions of the tree of runs, which can stop a batch midway (`step_limit_exceeded`): the check before the batch is on the iterations, not a reservation of the steps. At the answer to a manual step the iterations already run are counted as the steps already journaled, which is never fewer than the iterations that ran: a batch after the answer can be refused that an exact count would have accepted.
- **Empty lists.** An edge over an empty list runs no step, so the step cap never sees it, and a cycle of such edges (the save accepts a cycle that holds a forEach edge) would turn forever. Every such edge is counted: after 1000 in one uninterrupted walk the run fails with `for_each_limit_exceeded`. The count is not persisted: a run resumed after a manual answer counts again from zero, which still bounds every walk. The walk gives the event loop a turn at each one, and the stop of the daemon is checked at every edge followed, so the daemon keeps serving and can stop; the run ends `needs_review`.
- **A failed iteration stops everything.** The next elements never start; the step keeps its own code and the run fails with `for_each_iteration_failed`. The effects of the iterations that already ran stay: nothing is undone. An iteration interrupted by the stop of the daemon ends the run `needs_review`.
- **Trust.** The elements of a list a step produced are untrusted data: where a step output is refused (the arguments and environment of a script, the authority of an http url, the headers, the store identifiers), so is `{{item}}`; the save refuses it, and the runner checks again before it runs. The elements of an input are trusted like the input, except in a run an agent launched (see "The inputs of an agent run are untrusted").
- **The target** of a `forEach` edge is refused with `playbook_not_runnable` when it is a `manual` cell (a question per element). The output of the target under `steps.<id>` is the one of the last iteration that succeeded.

## subPlaybook cells

A `subPlaybook` cell runs another playbook as a run of its own and waits for it to end. The `inputs` of the cell are resolved in the parent (no secret, no untrusted data: the save refuses `{{steps.x.output}}` there with `untrusted_reference`) and masked with the secrets of the parent before the child sees them.

- **The child is checked like a start.** It must be a playbook of the same project (another project, or none, is `playbook_not_found`), approved at the instant it starts (`playbook_unapproved`), with no `manual` cell (`playbook_not_runnable`: nobody could answer for the parent). Its secrets are its own. The checks are made again once its secrets are read, in the turn of the event loop that journals it: a child edited, unapproved or out of capacity during the wait is refused and no run of it is written. The same turn requires the parent run to still run and its step to still be running: a parent whose playbook was deleted while the secrets of the child were read starts no child.
- **Depth and cycles.** The root run is level 0 and a child sits one level below its parent: 10 levels at most, and the 11th is refused with `playbook_not_runnable`. A playbook that is already above the call, or that calls itself, is refused the same way. A run holds its place while its child runs, so 4 runs at once (the default) allow a root and three nested levels of children.
- **A real run.** The child is journaled with `insertRun`, for the actor of the parent, and counts among the runs at once, the retention (`maxRunsToKeep`) and the activity log like any run. The parent keeps its own place while it waits, so with `maxConcurrentRuns = 1` a child is always refused with `playbook_run_busy` (the code of the step and of the run of the parent).
- **One budget per tree.** A root run carries the budget of every run it calls, at any depth and in any generation: the step executions of all of them count among the same 1000 (`step_limit_exceeded`), and the root starts at most 100 children in all (`sub_playbook_limit_exceeded` for the child over the budget). A child never starts with fresh counters. When a root parks on a manual cell, the budget it consumed so far (the steps of every run of the tree and the children started, among those that retention or a deletion removed since) is written in the output of the parked step, and the answer reloads it: a root's two sides of a manual question share one budget, across a restart of the daemon too. A run parked before that field existed (the field is absent) resumes from the steps of its own journal. A field that is present but out of its bounds (not an integer, below 0, above 1000 steps or 100 children) is an inconsistent journal: the answer closes the question, ends the run `needs_review` with the journal-only code `parked_tree_budget_invalid` (no wire code), and is refused with `manual_already_answered`; the run is never continued.
- **The answer.** The step answers `{ childRunId, status, errorCode?, output? }`. The result comes back from the execution of the child itself, never from its journal, so a child whose journal was pruned or deleted still answers. `output` is the output of the last step of the child that succeeded, as JSON text (a retry attempt that succeeded but whose `until` did not hold counts, as it does in the journal): untrusted data, so every text leaf goes through the masker of the parent before it is serialized again, then the whole text goes through it once more, then the control characters and the cap of 256 Kio. A failed child fails the step with `sub_playbook_failed` (the code of the child is in `errorCode`); a child that needs a review, because the daemon stops, ends the parent `needs_review`.
- **Secrets of the ancestors.** A child reads only its own secrets, but it masks the secrets of every run above it from its first write: the recognized forms of the values the parent resolved (plain, URL-encoded, base64, JSON-escaped, as for the secrets of a run) are masked in the journal of its child and of its grandchildren, whatever the child read them from. A value that was hashed, split, transformed or encoded again falls outside that contract, as it does for the secrets of a run.
- **Editing and deleting while a child runs.** A parent edited while its child starts or runs goes on with the content it was approved with: the approval is not asked again between two steps, and the edit takes effect at the next run. A playbook with a live run (running, or waiting for a human) cannot be deleted: the deletion is refused with `playbook_run_busy`, for the playbook of the parent, of the child and of every run of the tree, so the journal of a run that still has effects to make is never removed and no place among the runs at once is released while its work goes on. The deletion first ends the waits whose time is over, so a wait that already ended never refuses it. The check that journals a child still requires its parent run to run (`parent_gone` at the repository), as a second line of defense.
- **From the child to the parent, with no migration.** In the same transaction that journals the child run, the step of the parent is rewritten `{ childRunId, status: 'running' }`; it is settled with the final answer. `PlaybookRunRepository.parentOf(childRunId)` reads the parent step back through `json_extract` on the 10,000 most recent steps, and answers only when the child run exists and both runs belong to the same project. No route or tool calls it yet. Known limits: a child older than the 10,000 most recent steps no longer finds its parent; only a step that the runner wrote can name a child, since a script prints its text inside `output`.

## The tool cell

A `tool` cell is refused with `playbook_not_runnable` before anything is written. A run has no session, no role and no actor to give the tool, and the handlers of the MCP tools need a session; a cell that calls a tool comes with the actor and the role of a run (PBK-P3B-TOOL).

## The run tools

Five MCP tools let an agent start, cancel and read runs. A manager has the five. A worker has four: `cancel_playbook_run` is for managers only, so it is not published to a worker and, if a worker's session reaches the handler anyway, the call is refused with `not_a_manager` before any run is read or touched. The reviewer and the arbiter have none (they are in neither set). Every tool works on the project of the calling session: a playbook or a run of another project answers `playbook_not_found` / `playbook_run_not_found`, the answer of one that does not exist.

- **`run_playbook`** `{ playbook, inputs? }` (category `execution_external`). `playbook` is an id or an exact name of a playbook of the project. It starts the run through the same runner as the admin route and the triggers, with the launcher `agent` and the id of the calling session. Refused with `playbook_unapproved` (never approved, or edited since), `playbook_locked` (a human locked the playbook against agents), `playbook_not_runnable`, `playbook_run_busy` (the playbook already runs, or 4 runs are in progress), `playbook_waiting_backlog`, `playbook_review_backlog`, `playbook_conflict` (the playbook was edited and approved again while its secrets were read), and `invalid_body` for inputs the playbook does not declare, that lack a required one or that have the wrong type. The inputs are plain JSON within the bounds of the RUN of a trigger (at most 32 keys, 8 Ki characters, 6 levels). The approval, the project, the revision and the capacity are checked in the turn of the event loop that journals the run, after the secrets are read. The answer is `{ run: { id, playbook_id, status, started_at } }`; the run goes on in the background.
- **`run_playbook_cell`** `{ playbook, step_id, inputs? }` (category `execution_external`). Runs the ENTRY cell of an approved playbook as a run of its own (one journaled step, launcher `agent`): the edges after it never run. It is not a general single-cell runner: the entry cell is the one a full run starts with (the first cell of the flow, with no incoming edge), and any other `step_id` is refused. It goes through `beginRun` like `run_playbook`: approval, lock against agents, project, capacity, inputs checked, and the inputs of the run are untrusted (`untrusted_reference` where a step output is refused). Risk and decisions: a single cell can skip what stands before it in the flow, and the approval of a playbook covers its graph, not each cell alone. So (1) a playbook that holds a `manual` cell is refused whole with `playbook_not_runnable` (no human gate is skipped); (2) any cell but the entry cell is refused with `playbook_not_runnable`: a cell with a simple incoming edge can still stand behind a condition upstream, behind the fallback branch of a condition (the graph takes the first edge that matches), or behind a `forEach` branch that may be empty, and the incoming edges alone cannot rule that out, so there is no opt-in and no analysis of the path: only the cell a full run starts with runs alone; (3) a cell that reads the output of another step is refused with `playbook_not_runnable` (no step ran, and an agent can supply no fake output: there is no `seed_outputs`): the references are the `{{steps.<id>.<field>}}` tokens of its text fields and the paths on the left of its conditions (`predicate`, `retry.until`), read by segments: `steps`, `steps.<id>` and `steps.<id>.<field>` all read, the whole dictionary or the whole output of a step included; the tokens are found with the parser of the tokens, so a text that merely contains the letters `steps.` reads nothing. The `until` of a retry may read the output of the attempt of the cell itself (`steps.<its own id>`, with or without a field), which the runner publishes before it evaluates the predicate; it may not read another step nor the whole dictionary; (4) an unknown `step_id` is `playbook_cell_not_found`. What the run journals is not one step by construction: every attempt of a cell that retries is a journaled step (the run is one cell, not one attempt), a `subPlaybook` cell runs its child with the whole tree below it, and the launcher `agent` is written on the run and inherited by the children, as for `run_playbook`.
- **`cancel_playbook_run`** `{ run_id }` (category `destructive`, like `close_session`; managers only: a worker does not see the tool and is refused with `not_a_manager` if it calls it). Cancels a run of the project of the session that runs or waits for a human, and the whole tree it belongs to (naming a child cancels its root and every run below it): a retry backoff or a waitFor sleep ends at once, a script or a request in flight is killed, a running child ends, a pending question is closed, and a child whose start is still reading its secrets is not waited for: the read is abandoned, the signal of the tree is checked again right before the child is journaled, and no child is journaled nor announced once the tree was cancelled. When the preparation of a child fails while the tree is cancelled, the step of the parent ends with the cancellation verdict, not with the error of the preparation. The runs and their steps end `failed` with the code `run_cancelled`, which is the `error_code` of the run in the result and in the journal and not an error identifier of the protocol (no wire error code, no new status, no migration); the observer hears of each end, and the places among the runs at once are free when the call answers. A step whose attempt already ended before the cancellation (a retry that sleeps in its backoff after an attempt that finished) keeps the verdict of that attempt; the cancellation ends the run, not the past of its steps. The answer is a snapshot of the run taken when it was settled, so the retention of finished runs (`maxRunsToKeep`) purging the run at that very instant never turns a successful cancellation into an error. Two cancels sent while the same running tree is still stopping both succeed and answer the same ended run (the abort is idempotent and both wait for the same end); a cancel sent after the run ended, once its terminal journal exists, is `playbook_conflict`. On a run waiting for a human, the first cancel abandons the question synchronously and a later one meets the terminal status. The cancel of a wait settles the question of that run only, at one decision instant read once: a deadline reached at that instant ends the run as `manual_wait_expired` and the cancel of it is `playbook_conflict` (the end of the wait wins over a cancellation, as it does over an answer); the waits of other runs and projects are not swept by a cancel. The cleanup of a finished tree removes the registry entry only if it is still its own, so a run resumed while the tree that parked it is cleaning up stays cancellable. The first cause that stops a tree is frozen: a cancel admitted first keeps its verdict (`failed` with `run_cancelled`) when the daemon stops while the script is still terminating or at the last empty `forEach` transition, and a cancel sent once the daemon began to stop is `playbook_conflict`, the run keeping the verdict of the stop (`needs_review`, `interrupted`). A cancel does not undo an effect already acquired: the settlement, not the last operation, gives the status of the run, and the attempts of the journal say what ran. An approval of a manual step chooses the next edge, and resolves the tokens of the cells after it, on the exact output the answer writes for the parked step (`{ decision: 'approved' }`). A run that has already ended is `playbook_conflict`; a run that does not exist and a run of another project give the same `playbook_run_not_found`. A cancellation is not a manual answer: it needs no proof of a human gesture and never continues a run. No tool answers a manual step, and `playbook.resume_manual` stays human-only.
- **`get_playbook_run`** `{ run_id }`. The run with its journaled steps: `status`, `error_code`, and for each step `seq`, `step_id`, `status`, `error_code`, the instants. What a step produced is under `untrusted.output`, masked by the runner, capped at 2000 characters (`output_truncated: true` when cut) and shown for a settled step only; the steps are cut to fit 15 KB (`steps_truncated`). A run `waiting_manual` carries `awaiting: "human"`: it shows the outputs of the steps that already ended, and neither the question nor the internal output of the waiting `manual` step. The inputs of the run and the launcher are not shown.

What this lets an agent read, for operators: `get_playbook_run` and `list_playbook_runs` read every run of the project of the session, whoever launched it (a human through the admin API, a trigger, an agent) and whether or not the playbook is locked against agents; the lock binds what an agent may start or edit, not what it may read. The settled output of a step is shown as the runner stored it: masked with the values of the secrets the run resolved and with the shape-based layer, then capped. An output a script built from an input that a human typed, or any text a secret-free source produced, stays readable as long as it matches neither a resolved secret nor a recognised secret shape; the known limits of the masker (a value hashed, split or encoded again) apply to what an agent reads as they do to the REST view. Do not let a playbook print an input that must not be seen by the agents of the project.
- **`list_playbook_runs`** `{ playbook?, limit?, offset? }`. The runs of one playbook or of the whole project, newest first, without steps: 20 by default, 1 to 50, answer cut to fit 15 KB (`truncated`).

**The inputs of an agent run are untrusted.** In a run whose launcher is `agent`, and in every child below it (a child inherits the launcher of its root, kind and ref), a reference to `inputs.*` stands where the output of a step stands: it is refused with `untrusted_reference`, at run time (the save does not know who will launch the run), in the arguments and the environment of a script, the authority and the headers of an http request, its authentication, the identifiers of a store cell and the inputs of a `subPlaybook` cell. The same holds for `{{item}}` of a `forEach` edge whose list is `inputs.*`. The places that hold data accept an agent input: the body of an http request, the path and the query of a url whose authority is fixed, the values written to a store, the filter value of a store read, the text put to a human by a `manual` cell (it is shown to a human as a question, masked). The check is made when the step that holds the reference is reached, not when the run starts: an approved playbook can start through `run_playbook` and then fail with `untrusted_reference` on a later step (the default value of an input counts like a given one), and the steps before it have already produced their effects, which nothing undoes. `{{index}}` is a number the runner counts, not an input. A run launched through the admin API or by a trigger keeps trusting its inputs. An agent therefore cannot steer a command, a host or a credential through an input; it can still choose which approved playbook runs and the data it works on.

There is no tool that approves a playbook or answers a manual step: the answer needs the proof of a human (`playbook.resume_manual`), which an agent cannot give. The call is recorded in the activity log like any tool that acts; the argument `inputs` is withheld from the excerpt of the arguments whole: the recorder replaces it with a fixed text before the excerpt is built, and the excerpt writes that text as `[text len=10]` under the key `inputs`, whatever the keys and values the caller gave. That absence of the values is the property of the audit excerpt; no secret is read or shown by the tools. The lock against agents is checked at every start of a run an agent launched, a child at any depth included: a locked child called by an unlocked root fails the step of the root with `playbook_locked` and no run of the child is written. An input name the playbook does not declare is refused with the count of the names, never with the names.

## Who launched a run

Every run carries `launchedBy: { kind, ref }`, written once when the run is created and never changed (a database guard refuses any later update of the two columns, migration 074):

| `kind` | `ref` | Written when |
| --- | --- | --- |
| `admin_api` | `null` | the run starts through `POST /api/playbooks/:id/run` |
| `trigger` | the id of the trigger | a trigger fires its RUN `run_playbook` |
| `agent` | the id of the session that called `run_playbook` | an agent starts the run through the MCP tool |
| `unknown` | `null` | the run has no known launcher: it was created before migration 074, or its two columns were set back to NULL (a rollback of 074 followed by a new upgrade), or the database was replaced directly; no row is rewritten |

A run that a `subPlaybook` cell starts inherits the launcher of its parent, kind and ref as they are (the same actor kind too): a child of a run started through the admin API is `admin_api`, a child of a run fired by a trigger is `trigger` with the id of that trigger, a child of a run an agent started is `agent` with the id of the same session, at any depth. The agent launcher is not only a trace: a run it launched, children included, refuses the playbooks locked against agents (`playbook_locked`) and treats its inputs as untrusted (see "The run tools"). The launcher names who started the root of the tree, not the parent run.

`launchedBy` is part of the REST representation of a run (`POST /api/playbooks/:id/run`, `GET /api/playbook-runs/:id`, `GET /api/playbook-runs?playbookId=`). No MCP tool shows it and none changes it. The kind `agent` is written by `run_playbook` only (migration 076 widens the pair CHECK; a rollback of 076 reads an agent run as `unknown`, and first closes every agent run still running or waiting for a human: the run and its live steps become `needs_review` with the code `interrupted`, its pending question is `cancelled`, so no answer can resume a run whose agent provenance the rollback erases, even after 076 is applied again; the runs that already ended keep their journal, and a run of another provenance is left as it is).

Direct database maintenance (migrations 075 and 076): a CHECK on the pair refuses a row whose launcher the application could not read (`trigger` or `agent` without a ref, a ref on `admin_api` or `unknown`, a ref without a kind, any other kind). Two limits remain. An INSERT that omits both columns stores NULL and reads as `unknown`, like a pre-074 run. The guard fires on UPDATE only: `INSERT OR REPLACE`, or a DELETE followed by an INSERT, replaces the row and so replaces its attribution. No production path does either.

Rollback: applying the down of 074 drops the two columns, so a run kept through a rollback loses its attribution and reads `unknown` after the upgrade is applied again, even if its launcher was known before. Replacing the database file does the same for the runs it does not carry. The sentence "never changed" holds for the daemon and for any UPDATE, not for a rollback or a direct replacement of a row.

Known limit: this is a trace, not a barrier. The column authorises nothing and refuses nothing: no check reads it, and the approval digest and the digest of the flow do not depend on it (a test starts the same playbook by hand and by a trigger and finds the same digests). The id of a trigger names a trigger that may have been deleted since; the column keeps the id as it was.

## Limits

1000 step executions per tree of runs, retries, iterations and the steps of the children included (a flow stored outside the save path with an undocumented loop stops there with `step_limit_exceeded`), 100 elements per forEach edge, 1000 forEach iterations per run and 1000 edges over empty lists per uninterrupted walk, 10 levels of subPlaybook and 100 children per root, 4 runs at once and one per playbook (`playbook_run_busy`), 256 Ki characters of output per step, stdout and stderr together (the rest is dropped as it arrives, so memory stays bounded however the script prints, NUL and other control characters included, and the output ends with `[truncated]`; the characters count as printed, before any cleaning), `maxRunsToKeep` succeeded or failed runs per playbook. A run that `needs_review` is not pruned and does not count in `maxRunsToKeep`: its journal is the evidence of an effect nobody has examined. No route resolves it yet; it goes away only with its playbook. To keep the disk bounded without deleting evidence, at most 50 runs may await a review across all playbooks: at that count a new run is refused with `playbook_review_backlog` (retry `never`), nothing is written and no run is deleted. That cap is a gate at the start, not a ceiling: several runs already running (a root and its children, or runs that the stop of the daemon interrupts together) can move to review at once and pass it, and a child cannot park on a human, so the cap of parked runs per project concerns the roots only.

Order of the output treatment: the shape-based layer, then the masker on the output as printed (a secret that holds a CR, LF, tab or NUL is recognised whole, on stdout and on stderr), then the removal of the control characters. A secret too long for one regular expression is found by string search; the masker never throws.

A token is checked in its place again at run time: the output of a step never reaches the arguments or the environment of a script, whatever the way the flow was stored.
